# 酒馆完整输出翻译与原始设计还原

本文不是再设计一版简化模板，而是把 `酒馆完整输出.txt` 里原本复杂的输入/输出结构翻译成“源码设计说明”。目标是看懂它原来到底怎么组织 prompt、怎么分层、怎么让 AI 同时扮演主持人、小说作者、变量更新器和后台档案管理员。

说明：原文件包含大量成人向字段和示例。这里保留其“变量系统/状态机/提示词协议”的设计含义，不逐字复刻露骨描写，相关部分会用“亲密/身体状态/成人状态”等技术描述代替。

## 1. 原文件整体长什么样

`酒馆完整输出.txt` 不是单条普通 prompt，而是一份 SillyTavern 服务日志 + Chat Completion 请求内容。真正有价值的是请求里的 `messages`。

它大体长这样：

```js
Chat Completion request: {
  messages: [
    {
      role: "system",
      content: "SYSTEM INSTRUCTION: ..."
    },
    {
      role: "user",
      content: "=<role>user"
    },
    {
      role: "assistant",
      content: "历史对话 + 角色扮演格式 + 世界观规则 + 用户创角档案 + 变量状态 + 操作协议"
    },
    {
      role: "user",
      content: ""
    }
  ]
}
```

也就是说，它并不是只把“当前用户一句话”发给模型，而是把很多层信息一起塞进上下文：

1. 角色扮演历史。
2. 世界观和文风规则。
3. 用户创角档案。
4. 当前变量 JSON。
5. 当前阶段的专用协议。
6. 可选行动生成协议。
7. 变量更新协议。
8. 后台事件处理协议。
9. 示例输出。

这就是它复杂的根源：每轮请求都像一次“小型运行时重建”。

## 2. 输入源码的顶层结构

原文件里最核心的输入结构可以抽象成：

```text
角色历史/对话历史
---
当前用户输入或剧情触发
---
当前阶段专用协议
---
#当前剧情变量状态:
<status_current_variables>
当前完整变量 JSON
</status_current_variables>
---
附加协议：
- 行动选项生成
- 变量更新规则
- 后台事件处理
---
master_protocol:
强制最终输出顺序
```

它不是一个单 prompt，而是一组按顺序拼接的 prompt 模块。

更像这样：

```text
build_prompt() {
  append(roleplay_history)
  append(style_rules)
  append(current_player_input)
  append(phase_protocol)
  append(status_current_variables)
  append(options_generator_protocol)
  append(variable_update_protocol)
  append(event_handler_if_any)
  append(master_protocol)
}
```

这套设计的关键是：不同阶段插入不同协议，但变量状态和最终输出协议始终存在。

## 3. 创角阶段：character_creation_protocol

创角阶段是最复杂的一段。它的输入包括用户提供的创角档案：

```xml
<init_data>
```yaml
# AI任务指令：解析以下用户创角档案，生成开场白并初始化所有变量。

创角档案:
  核心人格:
    姓名: ...
    初始状态: ...
    人格状态: ...
    性格特质: ...
  魔法契约:
    使魔伙伴种类: ...
    代表色: ...
    核心能力: ...
  简要外貌:
    外貌关键词: ...
    肉体关键词: ...
  额外备注: ...
```
</init_data>
```

然后紧跟当前变量：

```xml
<status_current_variables>
{
  "进程": { "阶段": "创角阶段" },
  "世界": { "日期": 305, "威胁等级": 1 },
  "记录": { "已击败Boss计数": 0 },
  "名声": { "知名度": 0, "风评": 0 },
  "主角": {
    "核心状态": {},
    "身体部位状况": {},
    "道具栏": {},
    "生理状态": {},
    "快感状态": {}
  }
}
</status_current_variables>
```

### 创角协议的源码结构

原件里的 `character_creation_protocol` 结构大约是：

```yaml
character_creation_protocol:
  objective: "你是小说家、摄影师、数据架构师。解析创角档案，写开场白，并初始化变量。"

  ai_workflow:
    - step: 1 - 深度推演
    - step: 2 - 电影级序章生成
    - step: 3 - 数据架构与变量初始化
    - step: 4 - 最终输出与校验格式
```

它的高明处在于：创角不是“填表”，而是“先构思、再写正文、再把构思落库”。

### Step 1：深度推演

原文要求 AI 在正式输出前先在内部推演：

```yaml
- step: 1 - 深度推演
  instruction: |
    在下笔撰写正文与生成数据前，请基于用户输入的核心设定，
    在思考中完成以下推演，但不要在此处输出答案。
```

推演问题包括：

1. 核心能力如何体现在服装、武器、视觉符号上。
2. 身高、体态、服装材质如何自然变成画面。
3. 五官、气质、细节反应如何营造氛围。
4. 使魔和主角之间如何互动。

这一步的目的：先让 AI 生成“隐藏设定草稿”，再把它用于正文和变量。

### Step 2：电影级序章生成

这一段是写作控制器：

```yaml
narrative_and_camera_rules:
  - 特写切入
  - 推轨长镜头
  - 隐性叙事
  - 沉浸底线
```

翻译成人话：

1. 不要上来罗列设定。
2. 从局部细节开场。
3. 通过动作、环境、互动展示角色。
4. 不要提“系统/创建角色/属性面板”。
5. 不要在序章里擅自塞敌人、危机、事件钩子。

它相当于把小说写法写成导演指令。

### Step 3：数据映射表

这是创角阶段最“源码”的部分。它给了一张字段映射表：

```yaml
data_mapping_table:
  #[A组: 忠实映射 - 分析用户输入]
  - field: "姓名"
    path: "/主角/基本信息/姓名"
    constraint: "直接映射用户提供的姓名"

  - field: "人格状态"
    path: "/主角/核心状态/人格状态"
    constraint: "只能填善良或堕落"

  #[B组: 创意丰满 - 结合推演补全]
  - field: "年龄"
    path: "/主角/基本信息/年龄"
    constraint: "推演符合人设的年龄数据"

  #[C组: 复杂结构录入]
  - field: "长期身体/特殊改造"
    path: "/主角/永久性身体改造"
    constraint: "如果存在，使用 insert；如果不存在，跳过"
```

这张表的作用是把自然语言创角档案变成结构化变量。

它分三组：

1. A 组：用户给了什么就映射什么。
2. B 组：用户没给，但 AI 根据设定补全。
3. C 组：复杂对象，用 `insert` 写入 Map。

这是它复杂度很高但稳定的原因：它没有让 AI 自由发挥“该存什么”，而是列出必须落库的字段。

### Step 4：创角输出格式

创角阶段要求输出：

```text
正文开场白...

<UpdateVariable>
  <Analysis>
    1. 运镜与感官回溯：...
    2. 数据自洽性检查：...
    3. 设定入库检查：...
  </Analysis>
  <JSONPatch>[
    { "op": "replace", "path": "/主角/基本信息/姓名", "value": "..." },
    ...
    { "op": "replace", "path": "/系统状态/主角创建完毕", "value": true },
    { "op": "replace", "path": "/进程/阶段", "value": "幕间休息" }
  ]</JSONPatch>
</UpdateVariable>
```

注意最后两条：

```json
{ "op": "replace", "path": "/系统状态/主角创建完毕", "value": true }
{ "op": "replace", "path": "/进程/阶段", "value": "幕间休息" }
```

这说明创角完成后，阶段切换也是由 AI 输出 patch，然后后台应用。

## 4. 幕间阶段：intermission_life_protocol

创角完成后，变量里的阶段变成：

```json
{
  "进程": {
    "阶段": "幕间休息"
  }
}
```

于是 prompt 插入幕间协议：

```yaml
intermission_life_protocol:
  objective: "现在是幕间休息环节。请暂缓节奏，聚焦生活细节与角色内心，保持场景连贯。"

  current_rhythm:
    phase: "平稳的日常延续"
    guidance: "推进平静日常，不要擅自跳时间或换场景。"

  narrative_elements:
    elements:
      - 与使魔互动
      - 处理表世界身份的日常
      - 独处的平静时光

  polishing_instructions:
    - 幕间不要延续战斗/成人化强刺激描写
    - 如果存在长期异常状态，只作为背景滤镜轻微体现
```

这一段是阶段节奏控制器。

它明确告诉 AI：

1. 当前不是战斗。
2. 不要擅自推进到下一个大事件。
3. 不要一直沉溺前一阶段的强刺激内容。
4. 要利用幕间发展人设、人际关系和生活感。

这其实是在解决互动故事很常见的问题：AI 容易为了刺激不断升级剧情，导致没有“呼吸感”。幕间协议就是专门压节奏的。

## 5. 行动选项协议：options_generator_protocol

幕间阶段会额外插入一个“快速对话选项”协议：

```yaml
options_generator_protocol:
  objective: "在正文的末尾（变量更新块之前），生成玩家的可选行动列表。"

  format_strict:
    - 必须且只能使用 XML 格式包裹
    - 每一行一个选项
    - 不要编号
    - 不要方括号
    - 第一人称
    - 10-20 字

  option_matrix:
    1. [行动]: 推进主线
    2. [交互]: 和身边角色互动
    3. [探索]: 调查环境/道具/状况
    4. [私欲]: 个人爱好、小秘密、放松行为
```

输出格式被固定为：

```xml
<行动选项>
我去问问使魔的想法
我先整理一下随身物品
我看看房间里有什么
我想稍微休息一会儿
</行动选项>
```

它的位置要求很重要：

```text
正文
<行动选项>...</行动选项>
<UpdateVariable>...</UpdateVariable>
```

这样前端/脚本可以分别解析：

1. 正文：给用户看。
2. 行动选项：渲染成按钮。
3. 变量更新：后台应用。

这已经接近游戏引擎的输出分层了。

## 6. 通用变量更新协议

无论创角还是幕间，都会出现 `# 核心: 变量更新`。

它先告诉 AI 当前阶段：

```yaml
当前阶段: 【幕间休息】 | 人格: 善良

流程控制:
  规则: "【幕间休息】"
  状态: "和平缓冲期 (剧情进度: 3 / 10)"
  禁令: "严禁擅自修改 /进程/阶段 提前进入战斗"
```

然后列出可更新变量和规则。

### 日常数值规则

```yaml
/世界/世界观备注:
  类型: "Map (主题 -> 内容)"
  触发: "捕捉剧情中涌现的关键细节并持久化"
  逻辑: "使用 insert 登记；后续发展用 replace；失效用 remove"

/世界/日期:
  逻辑: "MMDD 数字"
  警告: "严禁 AI 修改，后台自动推进"

/名声/知名度:
  逻辑: "使用 delta 更新"

/主角/道具栏:
  类型: "Map"
  获得物品: insert
  消耗物品: remove
```

这部分把常规 RPG 变量全部 API 化。

### 身体/状态类变量

原文件有一大组成人向身体状态变量。抽象成技术设计后，它做的是：

```yaml
/主角/生理状态/当前生理动态:
  逻辑: "一句简短状态描写"
  操作: replace

/主角/身体部位状况:
  类型: "Map(部位 -> 状态)"
  逻辑: "每个部位单独更新"
  限制: "一次只更新唯一部位路径"

/主角/快感状态/快感值:
  类型: number
  操作: delta

/主角/快感状态/总高潮次数:
  限制: "一般禁止 AI 直接操作，由事件控制"

/主角/永久性身体改造:
  类型: Map
  操作: insert/replace/remove
```

你可以把这类设计泛化成任何游戏状态：

```yaml
/player/temporary_status:
  当前短期状态

/player/body_parts:
  部位状态 Map

/player/long_term_effects:
  长期效果 Map

/player/progress_tags:
  经验/倾向/熟练度 Map
```

它的重点不是字段是否成人向，而是“短期状态、部位状态、长期效果、数值经验”这四类变量分得很细。

## 7. master_protocol：最终总控

在大量规则之后，原件用 `master_protocol` 做总收束：

```yaml
master_protocol: "你已阅读上方的【当前任务】和各类【状态监控】。现在，请将所有分散的逻辑汇总，并严格按照以下结构，按顺序进行输出：1. 故事正文，2. <UpdateVariable> 块。"

story:
  instruction: "根据当前阶段和人设，进行故事演绎。"

UpdateVariable_block:
  instruction: "基于本次最新的故事输出，使用 JSON Patch 更新系统变量。"
```

这相当于 main 函数。

前面所有协议都是库函数，`master_protocol` 才是最后调用：

```text
main:
  read all protocols
  generate story
  generate action options if required
  generate UpdateVariable
```

### strict_rules

```yaml
strict_rules:
  - context_isolation: "仅根据刚刚输出的最新剧情更新变量"
  - no_meta: "变量块必须被标签包裹，正文中不能出现代码/系统/数据"
  - array_append: "数组追加必须用 /-"
```

这三条分别解决三个问题：

1. 防止 AI 根据旧剧情乱改状态。
2. 防止正文污染机器数据。
3. 防止 JSON Patch 数组追加格式错误。

### structure_protocol

它强制 `<UpdateVariable>` 里包含两块：

```xml
<UpdateVariable>
  <Analysis>
    - 指令与事件：...
    - 状态检查：...
    - 身体/物品/效果更新：...
    - 变量与设定检查：...
  </Analysis>
  <JSONPatch>[
    ...
  ]</JSONPatch>
</UpdateVariable>
```

`<Analysis>` 的意义不是让用户看推理，而是让 AI 先走一遍检查流程。它像 commit 前的 checklist。

## 8. 示例库 examples_library

原件在协议最后放了几个完整示例。

大概包括三类：

```yaml
examples_library:
  - scenario: "战斗中状态变化"
  - scenario: "特殊事件清理"
  - scenario: "幕间日常与世界观录入"
```

每个示例都包含完整 `<UpdateVariable>`：

```xml
<UpdateVariable>
  <Analysis>
    - 强制指令：无。
    - 状态检查：...
    - 变量检查：...
  </Analysis>
  <JSONPatch>[
    { "op": "delta", "path": "/主角/核心状态/体力值/当前", "value": -15 },
    { "op": "replace", "path": "/主角/身体部位状况/胸部", "value": "状态描述" },
    { "op": "delta", "path": "/主角/某数值", "value": 35 }
  ]</JSONPatch>
</UpdateVariable>
```

示例库的作用很大：

1. 让模型模仿 XML 包裹。
2. 让模型模仿 JSONPatch 数组格式。
3. 让模型知道不同剧情类型该改哪些变量。
4. 让模型学会先 Analysis 再 JSONPatch。

这比单纯写“请按 JSON 输出”稳定很多。

## 9. 后台事件：event_handler

原文件里还有一个很重要的机制：后台事件。

例子是“线索整理事件”：

```yaml
event_handler:
  event_name: "线索整理事件"
  task_type: "SILENT_BACKGROUND_PROCESS"

  narrative_guidance:
    instruction: "这是系统后台维护任务，不需要在叙事中体现"
    focus: "继续根据玩家上一条回复推进日常互动，玩家不应察觉后台整理"

  ai_backend_task:
    role: "严谨的系统档案管理员"
    instruction: "在完成正常正文后，在底部 JSONPatch 中整理世界观备注"
```

这是一种非常有意思的设计：让 AI 同时执行“前台叙事”和“后台维护”。

它要求 AI：

1. 正文照常写，不要让玩家察觉。
2. 在变量更新块里做资料整理。
3. 整理完必须移除事件，防止死循环。

对应强制 patch 模板：

```json
[
  {
    "op": "replace",
    "path": "/世界/世界观备注",
    "value": {
      "某NPC": "整理后的描述",
      "某地点": "整理后的描述"
    }
  },
  {
    "op": "remove",
    "path": "/系统状态/待处理事件/线索整理事件"
  }
]
```

这说明它有一个事件队列：

```json
"系统状态": {
  "待处理事件": {
    "线索整理事件": true
  }
}
```

后台或脚本把事件塞进去，AI 看到事件后执行相应任务，执行完再输出 `remove` 清掉事件。

这就是它做“自动维护”的源码思路。

## 10. 原始复杂设计的运行流程

把所有东西连起来，它的运行流程大概是：

```text
1. 后台读取存档变量
2. 判断当前阶段：创角 / 幕间 / 战斗 / 事件
3. 拼接对应阶段协议
4. 如果有待处理事件，插入 event_handler
5. 插入当前变量 JSON
6. 插入行动选项协议
7. 插入变量更新协议和示例库
8. 调用 AI
9. AI 输出：
   - 正文
   - 行动选项
   - UpdateVariable
10. 后台解析：
   - 正文展示给玩家
   - 行动选项渲染为按钮
   - JSONPatch 应用到变量表
11. 保存新变量
12. 下一轮重复
```

用伪代码写就是：

```python
def run_turn(user_input, state):
    prompt = []

    prompt.append(roleplay_history())
    prompt.append(global_style_rules())
    prompt.append(user_input)

    if state["进程"]["阶段"] == "创角阶段":
        prompt.append(character_creation_protocol())

    if state["进程"]["阶段"] == "幕间休息":
        prompt.append(intermission_life_protocol())
        prompt.append(options_generator_protocol())

    for event_name in state.get("系统状态", {}).get("待处理事件", {}):
        prompt.append(event_handler_protocol(event_name))

    prompt.append(render_current_variables(state))
    prompt.append(variable_update_protocol())
    prompt.append(master_protocol())

    ai_text = call_model(prompt)

    story = extract_story(ai_text)
    options = extract_xml(ai_text, "行动选项")
    patch = extract_json_patch(ai_text)

    validate_patch(patch, whitelist_rules)
    new_state = apply_patch(state, patch)

    save_state(new_state)

    return story, options, new_state
```

## 11. 原始输入/输出的“源码级接口”

如果按接口设计看，它至少有这些输入：

```ts
type PromptInput = {
  history: ChatMessage[];
  userInput: string;
  state: GameState;
  phase: "创角阶段" | "幕间休息" | "战斗" | string;
  persona: "善良" | "堕落" | string;
  pendingEvents: Record<string, boolean>;
  styleRules: string;
  phaseProtocol: string;
};
```

AI 输出则是：

```ts
type ModelOutput = {
  storyText: string;
  actionOptions?: string[];
  updateVariable: {
    analysis: string;
    jsonPatch: PatchOperation[];
  };
};
```

Patch 操作：

```ts
type PatchOperation =
  | { op: "replace"; path: string; value: unknown }
  | { op: "delta"; path: string; value: number }
  | { op: "insert"; path: string; value: unknown }
  | { op: "remove"; path: string };
```

状态结构：

```ts
type GameState = {
  进程: {
    阶段: string;
  };
  世界: {
    日期: number;
    威胁等级: number;
    世界观备注?: Record<string, string>;
  };
  系统状态?: {
    待处理事件?: Record<string, boolean>;
  };

  名声: {
    知名度: number;

  };
  主角: {

  };
};
```

这就是“复杂原本”的接口形态。

## 12. 它为什么复杂但有效

它复杂，是因为它同时解决了五个问题：

1. 写作风格  
   用叙事协议、镜头协议、文风要求控制正文。

2. 阶段节奏  
   用 `进程/阶段` 和阶段协议控制创角、幕间、战斗等节奏。

3. 变量一致性  
   用 `<status_current_variables>` + JSONPatch 保持状态同步。

4. 玩家交互  
   用 `<行动选项>` 生成下一步按钮。

5. 后台维护  
   用 `待处理事件` + `event_handler` 做资料整理、事件清理和自动任务。

它的核心不是某一句神奇 prompt，而是一套 prompt runtime。

可以理解为：

```text
SillyTavern 前端/脚本 = 游戏运行时
变量 JSON = 存档
阶段协议 = 当前场景逻辑
event_handler = 后台任务
AI = 文本渲染器 + 状态变更提案器
JSONPatch = AI 给运行时的指令
```

## 13. 如果要复刻原始复杂度，应按什么顺序做

如果你想做的不是最小版，而是接近这个原件的复杂版，建议顺序是：

1. 先做状态存档  
   保存 `state.json`，至少包含阶段、世界、角色、道具、事件队列。

2. 做 Prompt 模块化  
   不要把所有东西写死在一个字符串里。拆成：
   - global_style
   - phase_protocol
   - options_protocol
   - variable_protocol
   - event_protocol
   - examples

3. 做 Patch 解析器  
   从 `<UpdateVariable><JSONPatch>` 中提取 JSON 数组。

4. 做 Patch 校验器  
   检查路径白名单、类型、只读字段、delta 边界。

5. 做阶段机  
   根据 `/进程/阶段` 插入不同协议。

6. 做事件队列  
   后台可以写入 `/系统状态/待处理事件/事件名`，AI 处理后 remove。

7. 做行动选项解析  
   从 `<行动选项>` 抽出 4 行，渲染为按钮。

8. 最后才扩展复杂变量  
   不要一上来就做几十个状态字段。先跑通闭环，再加细分字段。

## 15. 一句话总结

原始复杂设计不是一个 prompt，而是一个分层运行时：

```text
历史上下文
+ 阶段协议
+ 当前变量快照
+ 行动选项协议
+ 变量 API 文档
+ 后台事件协议
+ 示例库
+ master_protocol
= 一次完整 AI 回合
```

AI 输出也不是一段文本，而是三种产物：

```text
玩家看的故事
+ 前端用的行动选项
+ 后台用的 JSONPatch
```

这就是它的“输入源码”和“输出源码”的真实设计方式。
