# 酒馆完整输出思路解析

本文基于 `酒馆完整输出.txt` 中暴露出的 SillyTavern 请求结构，拆解它的核心机制。重点不是复刻具体题材，而是抽象出一套你自己可实现的“AI 主持人 + 变量系统 + 输出协议”思路。

## 1. 变量如何写入写出，以及如何让 AI 能处理变量

它的变量系统本质上是“外部程序托管变量，AI 负责生成变更指令”。

也就是说，AI 并不真正保存变量。每一轮请求前，系统把当前变量完整或局部注入 prompt，例如：

```xml
<status_current_variables>
{
  "系统状态": {},
  "进程": {},
  "世界": {},
  "主角": {}
}
</status_current_variables>
```

AI 读到这块后，把它当作“当前游戏存档”。回复正文之后，再输出一个专门给程序解析的变量更新块：

```xml
<UpdateVariable>
  <Analysis>
    - 状态检查：本轮发生了什么
    - 变量检查：哪些字段应该变化
  </Analysis>
  <JSONPatch>[
    { "op": "replace", "path": "/主角/核心状态/体力值/当前", "value": 85 },
    { "op": "delta", "path": "/名声/知名度", "value": 3 },
    { "op": "insert", "path": "/主角/道具栏/药水", "value": 1 },
    { "op": "remove", "path": "/系统状态/待处理事件/某事件" }
  ]</JSONPatch>
</UpdateVariable>
```

程序再从 AI 输出里提取 `<JSONPatch>`，校验 JSON，应用到真实变量表中。下一轮再把更新后的变量表塞回 prompt。这个循环就是变量“写入写出”的核心。

### 变量读取

它靠三个层次让 AI 正确读取变量：

1. 当前值：`<status_current_variables>` 直接给出当前 JSON 状态。
2. 字段说明：在 prompt 后面列出各路径的含义、类型、更新规则。
3. 禁止项：明确告诉 AI 哪些字段只读、哪些不能主动修改、哪些只能由后台脚本处理。

例如它会说明：

```yaml
/世界/日期:
  逻辑: "记录当前游戏日期，格式为 MMDD 数字"
  警告: "严禁随意增减或改写为其他格式，后台脚本会自动推进"
```

这相当于给 AI 一份“变量 API 文档”。AI 不是凭感觉改状态，而是按路径、类型和规则生成操作。

### 变量写入

它没有让 AI 输出整份新状态，而是让 AI 输出“补丁”。这是非常关键的设计。

常见操作有：

```json
{ "op": "replace", "path": "/path/to/var", "value": "新值" }
{ "op": "delta", "path": "/path/to/number_var", "value": 10 }
{ "op": "insert", "path": "/path/to/object/new_key", "value": "内容" }
{ "op": "remove", "path": "/path/to/object/key_to_delete" }
```

这种写法有几个优点：

1. 省 token，不需要每轮重写整份状态。
2. 容易校验，程序可以拒绝非法路径和非法类型。
3. 容易追踪，每轮到底改了什么非常清楚。
4. 方便做自动逻辑，比如 `delta` 后由后台负责上下限、等级、事件触发。

### 让 AI 能处理变量的重点

重点不是“告诉 AI 这里有变量”，而是把变量系统设计成 AI 容易遵守的协议。

最重要的几件事：

1. 给当前变量快照  
   AI 必须看到当前状态，否则只能瞎猜。

2. 给路径白名单  
   哪些变量能改、怎么改、何时改，都要写成明确路径。

3. 给操作类型  
   不要只说“更新变量”，而要规定 `replace / delta / insert / remove`。

4. 给强制输出容器  
   用 `<UpdateVariable>`、`<JSONPatch>` 这种标签把正文和数据分离，方便程序解析。

5. 给本轮隔离原则  
   它反复强调“仅根据刚刚输出的这一段最新剧情进行变量更新”。这能防止 AI 翻旧账乱改。

6. 给分析检查清单  
   `<Analysis>` 不是给人看的废话，它是在逼 AI 先做自检：状态有没有变、事件有没有清、道具有没有得失、数值有没有变化。

7. 给示例库  
   它针对战斗、日常、事件清理等场景给了完整例子。模型会强烈模仿示例格式。

你自己做一版时，可以采用这个最小协议：

```text
输入：
1. 当前剧情阶段
2. 当前变量 JSON
3. 本轮用户输入
4. 可修改变量路径说明

输出：
1. 故事正文
2. <UpdateVariable>
3. <Analysis>本轮状态检查</Analysis>
4. <JSONPatch>JSON 数组</JSONPatch>
```

然后由你的程序做：

```text
读取旧变量 -> 拼 prompt -> 调 AI -> 提取 JSONPatch -> 校验 -> 应用补丁 -> 保存新变量
```

## 2. 他的话术如何让 AI 按他的方式思考

它的话术不是单纯写“你要写得好”。它把 AI 的工作拆成了角色身份、工作流程、判断标准、输出格式、禁止事项、示例模仿五个层次。

### 第一层：给 AI 一个复合身份

它会说类似：

```yaml
objective: "你是一位兼具顶级小说家、电影摄影师与严密数据架构师的 AI。"
```

这个身份设计很聪明，因为它同时绑定了三种任务：

1. 小说家：负责叙事、人物、语言。
2. 摄影师：负责镜头、感官、画面调度。
3. 数据架构师：负责变量、JSON Patch、状态一致性。

这样 AI 不会只顾写剧情，也不会只顾机械更新变量。它被要求同时承担“创作”和“记账”。

### 第二层：把思考拆成步骤

它不是让 AI 直接输出，而是写了 workflow：

```yaml
ai_workflow:
  - step: 1 - 深度推演
  - step: 2 - 正文生成
  - step: 3 - 数据架构与变量初始化
  - step: 4 - 最终输出与校验格式
```

这相当于把模型从“聊天模式”切到“执行流程模式”。每一步都有明确目标：

1. 先分析设定。
2. 再写正文。
3. 再把正文映射为变量。
4. 最后按固定格式输出。

尤其关键的是，它要求“先在思考中推演，但不要输出”。这会让模型在最终答案里少一些草稿痕迹，同时保持更稳定的结构。

### 第三层：把抽象审美变成可执行规则

它不会只说“写得有沉浸感”，而是拆成具体规则，例如：

```yaml
narrative_and_camera_rules:
  - 从局部特写切入
  - 镜头随角色动作拉开
  - 不要像面板一样罗列属性
  - 禁止打破第四面墙
```

这类话术的价值是：它把“风格偏好”翻译成“生成动作”。

普通 prompt 常见问题是只给形容词：

```text
写得生动、细腻、有张力。
```

酒馆这套更像导演分镜：

```text
从一个局部细节切入，通过动作展开环境和人物，不要直接列设定。
```

后者更容易被 AI 执行。

### 第四层：用检查清单约束 AI 的后处理

在变量更新前，它要求 AI 做类似检查：

```text
- 指令与事件：是否有待清理事件？
- 状态检查：时间、阶段、数值是否变化？
- 身体与物品：装备、道具、状态是否变化？
- 变量与设定：是否有新世界观需要记录？
```

这类检查清单很重要。因为 AI 很容易写完正文后忘记同步状态。检查清单等于把“读后归档”变成固定动作。

如果你自己做，可以改成更通用的版本：

```text
变量更新前必须检查：
1. 角色数值是否变化
2. 背包/装备是否变化
3. 任务/事件是否完成或新增
4. 场景/位置/时间是否变化
5. 是否产生需要长期记忆的新设定
6. 是否存在禁止修改的系统字段
```

### 第五层：用格式协议分离正文和机器数据

它最终强制输出：

```text
1. 故事正文
2. <UpdateVariable> 块
```

这一步非常关键。AI 的自然语言输出是不稳定的，但 XML 标签包裹的结构块相对容易解析。

它还明确说：

```text
变量更新块的内容必须完全包裹，不允许在正文中出现代码、系统、数据。
```

这能避免正文污染 JSON，也能避免用户看到一堆后台数据。

## 3. 你自己做一版时的可复用架构

你可以把它抽象成四个模块。

### A. 状态层

维护一份真实变量表，由程序保存，不交给 AI 自行记忆。

示例：

```json
{
  "system": {
    "phase": "daily",
    "pending_events": {}
  },
  "world": {
    "date": 103,
    "location": "home",
    "notes": {}
  },
  "player": {
    "hp": { "current": 100, "max": 100 },
    "mp": { "current": 50, "max": 50 },
    "inventory": {},
    "status": {}
  }
}
```

### B. Prompt 层

每轮拼出：

```text
# 当前任务
根据用户输入继续剧情。

# 当前变量
<status_current_variables>
{...}
</status_current_variables>

# 可修改变量规则
- /player/hp/current: 只能 delta
- /player/inventory/${item}: 获得用 insert，消耗用 remove
- /world/date: 只读，由后台推进

# 输出格式
先输出正文，再输出 <UpdateVariable>。
```

### C. Patch 层

让 AI 只输出补丁：

```json
[
  { "op": "delta", "path": "/player/hp/current", "value": -5 },
  { "op": "insert", "path": "/player/inventory/key", "value": 1 }
]
```

程序负责：

1. 解析 `<JSONPatch>`。
2. 检查是不是合法 JSON。
3. 检查路径是否在白名单。
4. 检查值类型是否正确。
5. 应用到变量表。
6. 保存。

### D. 思考约束层

给 AI 固定工作流：

```text
你必须按以下顺序处理：
1. 读取当前阶段、地点、角色状态
2. 根据用户输入生成本轮剧情
3. 只根据本轮剧情判断变量变化
4. 输出变量补丁
5. 不要修改只读字段
```

这个比单纯写“请保持状态一致”有效得多。

## 推荐你自己的最小模板

下面是一版干净、通用、容易接入程序的模板：

```text
你是一个互动故事主持人，同时也是状态机维护者。

你的任务：
1. 根据用户输入和当前变量继续故事。
2. 正文必须自然，不要暴露系统、变量、JSON、规则。
3. 正文结束后，输出变量更新块。
4. 变量更新只能基于你刚刚写出的本轮剧情。

<status_current_variables>
{{CURRENT_STATE_JSON}}
</status_current_variables>

可修改变量：
- /player/hp/current: 数字，只能使用 delta
- /player/mp/current: 数字，只能使用 delta
- /player/inventory/${item}: 物品表，获得用 insert，失去用 remove
- /world/location: 字符串，地点明确变化时 replace
- /system/pending_events/${event}: 事件完成后 remove

只读变量：
- /world/date: 不允许 AI 修改
- /system/phase: 除非任务明确要求，否则不允许 AI 修改

输出格式必须如下：

故事正文……

<UpdateVariable>
  <Analysis>
    - 本轮发生：
    - 数值变化：
    - 物品变化：
    - 事件变化：
    - 长期记忆：
  </Analysis>
  <JSONPatch>[
    { "op": "delta", "path": "/player/hp/current", "value": -1 }
  ]</JSONPatch>
</UpdateVariable>
```

## 最关键的结论

这套东西的核心不是 SillyTavern，也不是某个插件，而是一个循环：

```text
状态注入 -> AI 叙事 -> AI 输出补丁 -> 程序校验应用 -> 新状态再次注入
```

它让 AI “能处理变量”的关键，是把变量变成一套明确的读写协议，而不是依赖 AI 的记忆。

它让 AI “按指定方式思考”的关键，是把创作拆成流程，把风格拆成动作，把变量更新拆成检查清单，把输出拆成正文区和机器区。

如果你要自己做一版，优先实现这三个东西：

1. 当前变量注入。
2. JSONPatch 输出与校验。
3. 固定工作流 + 示例库。

先把这三件事跑通，再去加更复杂的事件系统、自动阶段推进、长期记忆整理、角色风格模板。这样整体会稳很多。
